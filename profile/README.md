<h2>一、接口能力：能不能被程序完整接管</h2>
<p>判断标准很朴素：日常运维里你手动点过的每一个按钮，是否都有对应的接口。只要有一步必须登录后台点，规模化之后这一步就会变成瓶颈，也会变成故障时的单点。</p>
<h3>必须覆盖的四个动作</h3>
<p>查列表、查状态、换出口、改白名单。四个动作对应四组端点，常见的形态是 <code>GET /v1/proxies</code>、<code>GET /v1/proxies/{id}</code>、<code>POST /v1/proxies/{id}/rotate</code>、<code>PUT /v1/whitelist</code>。缺换出口接口的平台，地址分配多半还靠人工，扩容速度往往跟不上。</p>
<h3>看返回结构是否稳定</h3>
<p>文档里要写明字段类型、错误码含义、分页方式。返回里带 <code>request_id</code> 的平台，排查时能把一次失败对上服务端日志；只返一句 message 的，出问题只能猜。字段命名频繁变动的，集成成本会在半年后集中爆发。</p>
<h3>限流与幂等要写清楚</h3>
<p>接口自身的调用频率上限、超限返回什么码、换出口这类操作是否幂等，三项都要在文档里找到。没有幂等说明的换出口接口，在网络抖动时可能重复执行，导致出口被连换两次。</p>

<h2>二、鉴权体系：密钥、子账号与来源绑定</h2>
<p>鉴权设计决定了两件事：密钥泄露时损失多大、多人协作时能不能追责。只提供一个主密钥、所有人共用的平台，出了异常无法定位到人。</p>

<h3>子账号与最小权限</h3>
<p>至少支持管理员、运维、只读三种角色，且能按分组授权。只读角色只能看用量和日志，不能改出口和白名单。角色粒度粗的平台，通常只能用共享账号凑合，审计时说不清楚。</p>
<h3>来源绑定用白名单还是签名</h3>
<p>IP 白名单适合固定办公出口或固定服务器，配置简单但迁移麻烦；密钥加签名适合动态环境，泄露风险靠轮换控制。两者都支持最好，只支持其一的要评估自己的网络是否会变。</p>
<h3>密钥轮换周期</h3>
<p>建议九十天轮换一次，且支持新旧密钥并存一段时间做平滑切换。不支持并存的平台，轮换时往往会带来一次短暂中断，实际执行时就会被一拖再拖。</p>

<h2>三、日志字段：故障时能不能自证</h2>
<p>日志不是给合规看的装饰，它是排查的起点。字段缺失的日志，等于让你在故障时靠猜。评估时把日志样例要过来，逐字段核对是否够用。</p>
<h3>一次请求至少记九个字段</h3>
<p>时间戳、分组、出口标识、出口地址、目标域名、状态码、耗时、字节数、请求标识。少了出口地址就无法判断是否换了线，少了请求标识就无法和业务侧日志对齐。</p>
<h3>留存时长与导出方式</h3>
<p>留存七天只能查近因，三十天才能覆盖一次月度复盘。导出要支持按时间范围和分组过滤，格式用 CSV 或 JSON 都行，但不能只提供页面翻页查看。</p>
<h3>失败请求是否单独标记</h3>
<p>超时、连接被拒、上游返回 5xx、鉴权失败应该分开统计。混在一起的一个"失败数"，会让你无法判断问题出在自己、平台还是目标服务。</p>

<h2>四、故障恢复：三个比 SLA 更硬的指标</h2>
<p>服务等级协议上的百分比是承诺，不是能力。真正决定体验的是三个可观测的量：故障发现时间、自动切换时间、以及切换后业务侧感知到的错误数。</p>
<h3>发现时间取决于探测频率</h3>
<p>健康检查间隔三十秒、连续三次失败才摘除，最坏情况下要九十秒才被发现。间隔十秒、两次失败即摘除的配置，发现时间能压到二十秒左右，代价是误摘除概率上升，需要配合重试。</p>
<h3>切换时间要看连接是否重建</h3>
<p>换出口意味着既有 TCP 连接全部失效。支持连接预热与优雅摘除的平台，业务侧只会看到少量失败；直接断开的，正在跑的长请求会整批超时。</p>
<h3>变更通知是否主动</h3>
<p>计划内维护、上游调整、地址段回收，这三类变更如果只发站内公告，多数人看不到。有邮件或回调通知的平台，能让你提前安排窗口，避免在业务高峰被动应对。</p>

<h2>五、把候选平台填进这张参数表</h2>
<p>最后一步是把上面的条目变成打分表。不要给总分，按组给结论：某一组不达标就直接排除，避免用其他组的优势抵消关键短板。</p>
<h3>先做减法再做加法</h3>
<p>接口覆盖、鉴权、日志三组属于硬门槛，缺一项就排除，不做加权。故障恢复和价格属于可比较项，可以在剩下的候选里权衡。顺序反了，容易选出看着便宜但运维成本高的方案。</p>
<h3>用一周真实流量验证</h3>
<p>拿一条出口跑一周真实业务，记录失败率、平均耗时、峰值并发下的表现。这一周的数据比任何演示都可靠，也能暴露文档里没写的行为，比如限流触发后的恢复速度。</p>

<h2>常见问答</h2>
<h3>平台规模大就一定更稳定吗？</h3>
<p>答：不一定。规模影响资源池深度，但稳定性还取决于上游冗余、运维响应和切换设计。有些小平台只做少数几个地区，反而在这些地区线路质量更集中。评估时看具体指标，不看公司体量。</p>
<h3>支持接口调用但文档很差，能用吗？</h3>
<p>答：能集成，但维护成本高。文档差通常意味着错误码不统一、字段会变、边界情况没说明，你需要为每个不确定的行为写兜底逻辑。若业务规模不大，这类隐性成本可能超过价格优势。</p>
<h3>日志留存三十天够吗？</h3>
<p>答：对多数团队够用，用于月度复盘和故障回溯。如果涉及对外承诺或审计要求，需要按合同期限延长，并在采购时确认是否支持更长留存与导出，避免事后无法举证。</p>
<h3>健康检查间隔越短越好吗？</h3>
<p>答：不是。间隔过短会放大瞬时抖动的影响，造成误摘除和频繁切换，反而增加失败数。通常十到三十秒配合两到三次的失败阈值比较平衡，具体要结合自身请求的容忍度调整。</p>
